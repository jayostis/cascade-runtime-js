# What a narrowing of the matcher's comparisons may skip, rule by rule

Read from the queries under `queries/matcher/` of cascade-vocabulary that the default rule list (`runtime/rule-list/cbbb992c-cba6-4825-baab-9ebcd1c4379e.ttl`) names, at cascade-vocabulary `fe845e31`. No query was changed: its text is hashed into `rec:queryHash`.

A narrowing skips the pairs it is sure the rule would not join. Two kinds are asked about:

- **By code**: compare a record only with records that share one of its codes. It is safe for a rule only if every pair the rule joins shares the very property the narrowing reads.
- **By time window**: compare a record only with records whose clinically relevant time (or period) falls in a window round its own. It is safe only if every pair the rule joins has times the window reaches, whatever a record that states no time does.

`Joins` is the number of Sames of that rule in `joins.golden.txt` (runs and kit pods). A rule with none there has nothing to judge a narrowing by; D2 adds a fixture before narrowing it.

Two findings rules sit in the same list, `DifferentResultValuesAtOneInstant` and `DifferentResultUnitsAtOneInstant`. They file findings, not Sames, so the golden holds none of theirs. Both key on the same `testCode` and the same instant, so a narrowing by code or by an equal-instant window is safe, as for `SameResult`.

Reading the table, D2's rule from the critical read holds: narrowing is per rule, from its key. A rule whose cell says unsafe keeps the full comparison for that kind of narrowing: `SameMappedCode`, `SameMappedCodeAndDate`, `SameConvertedCode`, `SameBrandGeneric`, `SameVariationThroughTable` and `SameNoteOrDocumentMasterIdentifier` by code; `SameBusinessIdentifierAndTestCodeWithinOneOrganization` by time; `SameSelfAssertedBaseUrlAndAuthorizationEndpointOnOneHost` by both. The same-server rule's key is the server itself, and the rules that read a table join through the table's row, not through the record's own code.

The default rule list names one query per rule; older rule lists, which a pod may still name, use the other files of `queries/matcher/` (the `key-joined-first`, `bound-per-side` and earlier forms). Each is the same rule with the same key, written to be evaluated differently, so the cells above hold for them.

To write the golden again after a change to the vocabulary's names or rules: `UPDATE_JOINS_GOLDEN=1 node --test packages/runtime/dist/test/scoped-runs.test.js` from the repository root after `npx tsc -b`, then read the diff of `joins.golden.txt`: a re-minted name should change lines and no more, and a join that appears or goes is a change of behaviour.
