# What a narrowing of the matcher's comparisons may skip, rule by rule

Read from the queries under `queries/matcher/` of cascade-vocabulary that the default rule list (`runtime/rule-list/cbbb992c-cba6-4825-baab-9ebcd1c4379e.ttl`) names, every row read again at cascade-vocabulary `740bb65c` (origin/main after the re-mint). No query was changed: its text is hashed into `rec:queryHash`.

A narrowing skips the pairs it is sure the rule would not join. D2 narrows pairs, never a query's input: three kinds of rule read records or table rows outside the pair, and a query given only the pair's two records would answer differently. Three kinds are asked about:

- **By code**: compare a record only with records that share one of its codes. It is safe for a rule only if every pair the rule joins shares the very property the narrowing reads.
- **By time window**: compare a record only with records whose clinically relevant time (or period) falls in a window round its own. It is safe only if every pair the rule joins has times the window reaches, whatever a record that states no time does.
- **By record kind**: compare a record only with records of its `cascade:recordKind`. It is safe only for a rule whose query holds that filter (the column `Kind filter`).

`Joins` is the number of lines of that rule in `joins.golden.txt` (runs and kit pods). A rule with none there has nothing to judge a narrowing by; D2 adds a fixture before narrowing it.

`Outside the pair` names what the query reads besides the two records of a candidate pair: a table version's rows (the narrowing must keep a record whose code the table maps to another's), the other records the query gives a record its moments or its comparison from, and organization records.

Two findings rules sit in the same list, `DifferentResultValuesAtOneInstant` and `DifferentResultUnitsAtOneInstant`. They file findings, not Sames, and `joins.golden.txt` holds their findings as `finding` lines (five today, all of one run). Both key on the same `testCode` and the same instant, so a narrowing by code or by an equal-instant window is safe, as for `SameResult`, and neither has a record-kind filter.

Reading the table, D2's rule from the critical read holds: narrowing is per rule, from its key.

- **By code**, a rule whose cell says unsafe keeps the full comparison: `SameMappedCode`, `SameMappedCodeAndDate`, `SameConvertedCode`, `SameBrandGeneric`, `SameVariationThroughTable` and `SameNoteOrDocumentMasterIdentifier`.
- **By time**, `SameBusinessIdentifierAndTestCodeWithinOneOrganization` and `SameNoteTypeAndTextGrownWithinOneOrganization` keep the full comparison; `SameSelfAsserted...OnOneHost` keeps it by both.
- **By record kind**, only a rule whose `Kind filter` cell says yes may be narrowed by kind. Every rule that reads a result, a note or a server has none, and R21 (`SameNoteOrDocumentMasterIdentifier`) has no filter of any kind: two records of different kinds that carry one typed identifier join.
- **Outside the pair**, `SameBusinessIdentifierAndTestCodeWithinOneOrganization` (`?groupRecord`), `SameNoteTypeAndTextGrownWithinOneOrganization` (`?witness1`, `?witness2`), `SameProductCode` and `SameVariationThroughTable` (the current table version) must have what they read left whole: D2 narrows the pairs a rule compares, not the records the rule's query reads.

The same-server rule's key is the server itself, and the rules that read a table join through the table's row, not through the record's own code.

`runtime/test/joins-extra/note-master-identifier` holds R21's run, which no story of the vocabulary has: it is read as its own source by `storyRuns()` in `scoped-runs.test.ts`. A change of the vocabulary's story needs no change of it, and it is no vocabulary story.

The default rule list names one query per rule; older rule lists, which a pod may still name, use the other files of `queries/matcher/` (the `key-joined-first`, `bound-per-side` and earlier forms). Each is the same rule with the same key, written to be evaluated differently, so the cells above hold for them.

To write the golden again after a change to the vocabulary's names or rules: `UPDATE_JOINS_GOLDEN=1 node --test packages/runtime/dist/test/scoped-runs.test.js` from the repository root after `npx tsc -b`. The run writes the file and fails on purpose; read the diff of `joins.golden.txt` (a re-minted name should change lines and no more, and a join or a finding that appears or goes is a change of behaviour), then run the file again without the variable. A change of a vocabulary story that moves a Same or a finding is a pair of pull requests, as the vocabulary's rules for a change the runtime must follow say: the vocabulary's names this runtime's pull request on a `Depends-On:` line, which regenerates the golden.
